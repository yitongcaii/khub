## 2. 沟通协议（最重要，照做）

- **极简命令驱动**：常用单字确认（"要""改了吗"），别寒暄、别铺陈。
- **结论先行**：先给结论 / 方案 / 表格，再给支撑，不绕。
- **结构化 + 定量**：偏好表格、状态标记 ✅⚠️、可验收的量化指标。
- **确认式结构**：改动确认 → 关键校验 → 建议 → 下一步。
- **排错直给**：直接贴错误码或 @image 截图，要我**直接修且不破坏现有功能**，改完必须验证闭环。
- **不确定就先问**：常说"如果有不明确的可以问我"，也欢迎我先澄清再起草。

---

## 4. 视觉 / 审美偏好

- **活泼有活力**，排斥标准 / 正式 / 模板化样式；文案偏好喜庆、热闹、有记忆点。
- **UI 像素级**：会指定精确 padding（1px / 2px）、字体 px，对布局差异高度敏感。
- **HTML 交付**：暖色系、可编辑、含自动保存草稿 + 导出；卡片风格 = 渐变标题 + hover 效果 + 序号角标。
- **链接规范**：统一走 GitHub Pages 渲染链接，**排斥 /blob/ 源码链接**。
- 交付物多为增量迭代（多轮逐步完善），而非一次性大版本。

## 7. 协作雷区（Don't）⚠️

- ❌ 冗长寒暄、目录列表、多余解释
- ❌ 重复已有方案（同一主题给过的，不想再看第二遍）
- ❌ 自行修改可编辑字段（活动主题等人工所有权）
- ❌ 改动后不确认是否生效（闭环验证是硬性要求）
- ❌ 以"修复"为名破坏现有功能
- ❌ 单一观察样本就下高置信结论（要边验证边推进）

## 9. 典型任务 SOP 模板

> 以下为高频重复任务的"骨架"，照着走即可，不必每次重新发明。

### 9.1 新人发展答辩 70 天自动化跑批

**触发**：每月检测企微智能表格「新人看板」中 `答辩状态 = 待安排` 且 `入职日期 + 70 天 ≤ 今天` 的行。

| 步骤 | 动作 | 关键参数 / 注意 |
|---|---|---|
| 1 检测 | 读看板，筛待安排且到期行 | 导师列为文本，多名导师用 `、` 分隔，需拆分 |
| 2 提案 | **不自动执行**，先算会议日 = 今天+7 个工作日 14:00–14:30，受邀人 = 新人+导师去重 | 新人兼评委则去重；展示给用户等确认 |
| 3 确认 | 等 y 说「执行」 | 未确认前不建会/不建群/不发消息 |
| 4 建会 | 腾讯会议 `contact_search` 解析导师 RTX→open_id；`schedule_meeting` | 标题前缀 `（时间预留）<答辩类型>-<姓名>`；hosts=蔡依彤本人 token（即主持人，无需 host transfer）；`auto_record_type=cloud` |
| 5 回填 | 写看板：会议日期(ms 时间戳)/会议号/链接/`答辩状态=已安排` | 覆盖旧残留字段 |
| 6 建群 | 企微客服号通道 `create_chat` | 群名=`新人发展答辩沟通群-<姓名>`；别名=`rookie-defense-<rtx>`；成员=新人+导师+客服号 |
| 7 推送 | 发两条 rich_text @名单 | ① 材料提醒 ② 会议链接（填真实 join_url / code） |
| 8 收尾 | 客服号保留不退群 | — |

⚠️ **坑**：① 云录制仅"请求"，企业后台是否真录取决于 IT 开关；② 企微聊天消息被企业禁用，触达只能走客服号通道或会议邀请；③ GBK 终端跑 wecom-api 脚本会 `UnicodeEncodeError`，改用 Python API + utf-8 stdout。

### 9.2 活动 HTML 产出 & GitHub Pages 交付

1. 写 HTML：暖色系；卡片 = 渐变标题 + hover 效果 + 序号角标；含可编辑字段 + 自动保存草稿(localStorage) + 导出。
2. 本地 / GitHub Pages 预览验证（**排斥 /blob/ 源码链接**）。
3. 推送到 `yutttyi/activities-html`（或对应仓库）。
4. 交付渲染链接 `https://<user>.github.io/<repo>/<file>.html`。

⚠️ **坑**：① 中文文件名在 GitHub Pages 会 404，统一英文文件名；② 活动主题等可编辑项保留人工所有权，AI 不擅自改。

### 9.3 企微客服号建群 + @提醒推送

**前提**：`~/.wecom-api/secrets/credentials.json` 已配（corpid / service_id / secret）。

1. 取 token（公网 `qyapi.weixin.qq.com/cgi-bin/gettoken`，缓存 2h）。
2. `create_chat(成员 + 客服号)` → 拿 chatid，按别名写 `~/.wecom-api/data/chat_registry.json`。
3. 发 `rich_text` / `markdown` 消息，`@` 名单用 RTX 名。
4. `update` 改群名；`quit` 退群（可选）。

⚠️ **坑**：GBK 终端 emoji 报错 → 用 Python API + `sys.stdout` utf-8 包装，别直接跑 CLI 脚本。

### 9.4 抽奖应用 UI / 功能迭代

**栈**：Vue3+Vite 前端 / Express+SQLite 后端，Railway + GitHub Pages。

1. 读现有组件（PrizeCard / AdminPage）定位改动点。
2. 按 y 指定像素值改（padding 1/2px、字体 px），先删减后修复。
3. 本地构建验证 **不破坏现有功能**。
4. 部署 Railway（Push 触发）。
5. 验证闭环，回 y「改了吗」式确认。

⚠️ **坑**：UI 差异 y 高度敏感，必须精确对齐；改动必验证。

### 9.5 知识研究 → 结构化输出（ima / 乐享）

1. 明确问题 / 主题（如活动策划框架）。
2. ima 或 lexiang 检索，**标注出处 / 章节**。
3. 优先原文片段或源链接，不摘要糊弄。
4. 结构化分类输出（表格 + 标签）。
5. 沉淀为案例卡 / READ 知识运营模型。

⚠️ **坑**：不编造出处；单一观察样本低置信，边验证边推进。

## 10. 验收清单模板

> 交付前逐条打勾，未达标不打回但标注 ⚠️。每条对应 y 的"定量验收 + 验证闭环"硬要求。

### 10.1 活动方案验收
- [ ] 目标 / 背景明确，给出量化指标（参与人数 / 触达 / 满意度）
- [ ] 规则 / 亮点 / 流程完整（非仅活动名罗列）
- [ ] 时间线 + 分工 + 预算 三件套齐全
- [ ] 风险预案 + 归档 / 复盘机制
- [ ] 文案喜庆热闹、非模板化
- [ ] 输出格式符合要求（Word / HTML / 表格）

### 10.2 活动 HTML 交付验收
- [ ] 暖色系；卡片 = 渐变标题 + hover + 序号角标
- [ ] 可编辑字段 + 自动保存草稿(localStorage) + 导出
- [ ] 移动端 / 桌面端布局对齐（y 像素级敏感）
- [ ] 中文文件名已转英文（防 GitHub Pages 404）
- [ ] 交付渲染链接（非 /blob/ 源码）
- [ ] 活动主题等人工字段未被 AI 篡改

### 10.3 抽奖应用改动验收
- [ ] 改动点对照需求，无多余改动
- [ ] 现有功能未被破坏（本地构建通过）
- [ ] 像素值按指定（padding / 字体 px）
- [ ] Railway 部署成功，线上验证闭环
- [ ] 回 y「改了吗」式确认

### 10.4 新人答辩跑批验收
- [ ] 仅处理 `待安排` 且到期行
- [ ] 会议日 = 今天+7 工作日，受邀人去重正确
- [ ] 建会标题带 `（时间预留）` 前缀、云录制开
- [ ] 看板回填（日期 / 号 / 链接 / 状态）无旧残留
- [ ] 群名 / 别名规范，消息 @名单正确
- [ ] 客服号保留、无测试消息外泄

### 10.5 知识研究输出验收
- [ ] 标注出处 / 章节，优先原文或源链接
- [ ] 结构化分类（表格 + 标签）
- [ ] 无编造、无低置信单样本结论
- [ ] 可沉淀为案例卡 / READ 知识运营模型
